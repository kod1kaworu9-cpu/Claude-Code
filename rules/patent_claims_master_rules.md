# 請求項 組み立てマスタールール

**担当：特許エンジニア（Patent Engineer）**
**最終更新：2026-02-26**

---

## 0. 大原則

1. **広く書いてから狭める** — 独立請求項は可能な限り広く、従属請求項で段階的に限定する
2. **必要最小限の構成要素** — 独立請求項に入れる要素は権利取得に不可欠なものだけ
3. **一貫した用語** — 同じ概念には同じ言葉を使い続ける（明細書全体で統一）
4. **審査官・裁判官を意識する** — 読んだだけで技術的範囲が明確にわかる文章にする
5. **将来の侵害者を想定する** — 競合他社が回避しにくいクレーム設計を意識する

---

## 1. 請求項の基本構造

### 独立請求項（メインクレーム）

```
【請求項1】
[前提部]　〇〇であって、
[特徴部]　△△を備え、
　　　　　□□することを特徴とする、
[カテゴリ]〇〇。
```

**例：**
```
【請求項1】
プロセッサとメモリを有する情報処理装置であって、
前記メモリには、前記プロセッサに、
　ユーザーの入力を受け付けるステップと、
　受け付けた入力を解析するステップと、
　解析結果を出力するステップと、
を実行させるプログラムが格納されていることを特徴とする、
情報処理装置。
```

### 従属請求項（サブクレーム）

```
【請求項N】
請求項[番号]に記載の〇〇において、
[追加・限定する構成]をさらに備える、〇〇。
```

---

## 2. カテゴリの選択ルール

| カテゴリ | 使う場面 | 例 |
|---------|---------|-----|
| **物（装置・システム）** | ハードウェア・構造物 | 装置、システム、デバイス |
| **方法** | プロセス・手順 | 製造方法、情報処理方法 |
| **プログラム（ソフトウェア）** | コンピュータに実行させる処理 | プログラム、記録媒体 |
| **物質・組成物** | 化学・材料 | 化合物、組成物 |

> **鉄則：** 同じ発明を「装置」「方法」「プログラム」の3カテゴリで出願すると権利範囲が広がる。

---

## 3. 請求項の階層設計

```
請求項1（独立）　← 最も広い権利範囲
　└ 請求項2（従属）　← 重要な実施形態A
　　└ 請求項3（従属）　← さらに限定した形態
　└ 請求項4（従属）　← 重要な実施形態B
請求項5（独立）　← 別カテゴリ（方法）
　└ 請求項6（従属）
請求項7（独立）　← 別カテゴリ（プログラム）
```

**ポイント：**
- 独立請求項は3〜5個が理想（物・方法・プログラム＋バリエーション）
- 従属請求項は審査での補正の逃げ道として機能する
- 請求項の総数は20〜30が目安（超過すると審査請求料が加算）

## 4. 言葉の選び方ルール

### 4-1. 広くする表現

| 目的 | 使う表現 | 避ける表現 |
|-----|---------|-----------|
| 手段を限定しない | 「取得する手段」「処理部」 | 「CPUが計算する」 |
| 材料を限定しない | 「導電性材料」 | 「銅」 |
| 数値を限定しない | 「所定の閾値」 | 「100度以上」 |
| 形状を限定しない | 「板状部材」 | 「正方形の板」 |

### 4-2. 必須 vs 任意の表現

| 意味 | 表現 |
|-----|-----|
| 必須の構成要素 | 「〜を備え」「〜を有し」「〜からなり」 |
| 任意の構成要素 | 「〜をさらに備えてもよい」（従属請求項に回す） |
| 動作を示す | 「〜するように構成された」「〜する手段」 |

### 4-3. 禁止ワード・注意ワード

| 禁止・注意 | 理由 | 代替表現 |
|-----------|------|---------|
| 「等」「など」 | 範囲が不明確 | 列挙するか削除 |
| 「約」（数値の前） | 明確性欠如のリスク | 数値範囲で表現 |
| 「好ましくは」 | 必須か任意か不明確 | 従属請求項に移す |
| 「本発明は」 | 発明の範囲を限定するリスク | 削除 |
| 商品名・固有名詞 | 権利範囲が極端に狭くなる | 技術的特徴で表現 |

## 5. 機能的クレームの書き方

機能・効果でクレームを書く際のルール：

```
✅ 良い例：
「ユーザーの認証情報を検証する認証手段」

❌ 悪い例：
「ユーザーが正しくログインできるようにする手段」
（効果を書いており、技術的構成が不明確）
```

**機能的クレームのチェックリスト：**
- [ ] 明細書に対応する具体的実施例が記載されているか
- [ ] 機能が技術的に特定できるか
- [ ] 当業者が実施できる範囲か

## 6. ソフトウェア特許のクレーム

### 推奨フォーマット（プログラムクレーム）

```
【請求項X】
コンピュータに、
　[処理ステップ1]するステップと、
　[処理ステップ2]するステップと、
　[処理ステップ3]するステップと、
を実行させるためのプログラム。
```

### 推奨フォーマット（方法クレーム）

```
【請求項X】
コンピュータが、
　[処理ステップ1]するステップと、
　[処理ステップ2]するステップと、
　[処理ステップ3]するステップと、
を含む情報処理方法。
```

## 7. 審査対策ルール

### 7-1. 新規性・進歩性を確保するための設計

```
Step 1: 先行技術との差分を明確に特定する
Step 2: 差分を構成要素として請求項に盛り込む
Step 3: 差分が効果に結びついていることを確認する
Step 4: 差分が過度に狭くなっていないか確認する
```

### 7-2. 拒絶対策の階層

```
独立請求項1　← まずここで広い権利を狙う
　└ 請求項2　← 拒絶時の第1補正候補
　　└ 請求項3　← 拒絶時の第2補正候補（確実に登録可能な範囲）
```

> **鉄則：** 請求項3は出願前に「これなら確実に通る」と判断できるレベルまで限定しておく。

## 8. 最終チェックリスト

請求項を完成させる前に以下を確認する：

### 形式チェック
- [ ] 1請求項1発明の原則を守っているか
- [ ] 文末が「〇〇（カテゴリ）。」で終わっているか
- [ ] 前の請求項を正しく引用しているか
- [ ] 用語が明細書全体で統一されているか
- [ ] 「前記」の初出の定義が明細書にあるか

### 内容チェック
- [ ] 独立請求項は必要最小限の要素のみか
- [ ] 重要な実施形態が従属請求項でカバーされているか
- [ ] 物・方法・プログラムの3カテゴリをカバーしているか
- [ ] 先行技術との差分が明確に記載されているか
- [ ] 競合他社が容易に回避できない構成になっているか

### リスクチェック
- [ ] 実施例が1つしかなく権利範囲が狭くなっていないか
- [ ] 不要な限定が入っていないか
- [ ] 明細書にサポートされていない記載がないか

---

## 9. よくある失敗パターン

| 失敗 | 内容 | 対策 |
|-----|------|------|
| **過度な限定** | 実施例をそのままクレームに書く | 抽象化して上位概念で表現 |
| **サポート不足** | 請求項の範囲が明細書の実施例を超えている | 明細書に複数の実施例を追加 |
| **用語不統一** | 同じ構成要素に複数の名称を使う | 用語集を作成して統一 |
| **従属先ミス** | 従属請求項が引用する番号を間違える | 階層図を作って確認 |
| **目的・効果の混入** | 請求項に「〜のために」と目的を書く | 技術的構成だけに絞る |
